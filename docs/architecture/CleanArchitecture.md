# 객체 지향 프로그래밍
- 요약: 다형성과 상속에서 많은 편리한 기능을 제공한다. 
- 좋은 아키텍쳐를 만드는 일은 OO 설계 원칙을 이해하고 응용하는 데서 출발한다.
- OO의 본질을 설명하기 위해 캡슐화, 상속, 다형성을 차례대로 살펴보자

## 1. 캡슐화
- 결론: OO(Object-Oriented)는 캡슐화에 이점이 없다.
- C와 C++을 비교하여 보자.

|     | C++                         | C                      |
|-----|-----------------------------|------------------------|
| 분류  | Object-Oriented Programming | Structured Programming |
| 캡슐화 | 헤더 파일, 클래스, 접근제어자           | 헤더 파일, 구조체             |

### C++의 특징
- 컴파일러가 클래스의 인스턴스 크기를 알 수 있어야 합니다
- 이 특징으로 인해 클래스의 멤버 변수를 해당 클래스의 헤더 파일에 선언해야 합니다
```C++
class Node{
public:
    Node(int num);
private:
    int num;    
};
```
- 아래의 C와 비교하면 완전한 캡슐화가 깨진 것을 알 수 있습니다.
```C
struct Node;
struct Node* makeNode(int num);

```
- 접근 제어자는 OO의 불완전한 캡슐화를 보완하기 위한 임시방편입니다.
- 자바와 C#은 선언과 정의를 구분하는 것이 불가능합니다.
- 파이썬, 루비, 자바스크립트 등 많은 OO 언어가 캡슐화를 강제하지 않습니다

## 2. 상속
- 결론: 새로운 개념을 만든 것은 아니지만, 많은 편의성을 제공한다.
- C언어에서도 멤버 변수의 순서를 같게 하여 특정 데이터 구조가 파생된 것처럼 구현할 수는 있다.
- 실제로 C++에서 위 방법으로 단일상속을 구현했으며, OO 출현 이전부터 많은 프로그래머가 사용하고 있다.
- 하지만 다중 상속 구현에 굉장한 어려움이 있으며, 형변환도 직접 해주어야 한다.

## 3. 다형성
- 결론: 새로운 개념은 아니지만, 안전하고 편리하게 적용 가능하다
- 프로그래머들은 다형적 행위를 수행하기 위해 함수를 가리키는 포인터를 사용해왔다
- 천공카드에서 자기테이프로, 입출력 장치 독립성을 지원하기 위해 고안된 플러그인 아키텍쳐는 등장 이후 대부분의 운영체제에 적용되었다.
- 하지만 함수포인터를 사용할 경우 생기는 초기화, 호출 등의 문제로 많은 프로그래머가 이러한 개념을 적용하지 않고 있었다.

### 의존성 역전
- 전형적인 호출 트리에서 소스 코드의 의존성의 방향은 제어 흐름을 따르게 된다
- 하지만 인터페이스를 개입시키면 상, 하위 모듈의 의존성이 모두 인터페이스를 향하게 된다
- 덕분에 분리된 컴포넌트로 독립적으로 컴파일 및 배포할 수 있다. 

## 결론
- 소프트웨어 아키텍트 관점에서 OO란 다형성을 이용하여 전체 시스템의 모든 소스 코드 의존성에 대한 절대적인 제어 권한을 획득할 수 있는 능력이다.

# C++의 객체지향: 다형성

- 개요: 다형성을 중심으로 C++에서는 어떠한 방식으로 객체지향의 특징을 구현하고 있는지

## 다형성, virtual
```C++
class Parent{ // basic
public:
    virtual void run(){
        cout<<"parent run"<<endl;
    }
    
    void walk(){
        cout<<"parent walk"<<endl;
    }
    
    virtual ~Parent(){
    
    }
};

class Child: public Parent{ //derived
public:
    void run(){
        cout<<"child run"<<endl;
    }
    
    void walk(){
        cout<<"child walk"<<endl;
    }
    
    ~Child(){
    }
};

int main(){
    Parent* parent_ptr;
    Child child;
    parent_ptr = &child;
    
    //런타임에 바인딩이 수행되는 가상함수
    parent_ptr->run();
    
    //컴파일 중 바인딩이 수행되는 비가상함수
    parent_ptr->walk();
    
    return 0;
}
```
- 위 코드의 실행 결과는 아래와 같다

```C++
child run
parent walk
```

- run 함수는 virtual 키워드를 통해 런타임 다형성을 보장한다
### 동작: vtable과 vptr
- 가상 함수가 호출되면 vptr을 통해 vtable에 접근하고, vtable에서 함수의 포인터를 찾아 이를 호출합니다.
#### vtable, 가상 함수 테이블
- 클래스에 가상함수가 있으면 컴파일러는 자동으로 이 클래스에 대한 vtable을 생성합니다.
- 이들은 가상함수들의 주소를 저장하며, 모든 가상 함수 호출은 이 테이블을 거치게 됩니다.
- 파생 클래스의 생성자는 생성하려는 객체의 vtable을 자신의 함수로 덮어씁니다.
#### vptr, 가상 함수 테이블 포인터
- 클래스의 객체가 생성될 때마다 vptr이 객체의 데이터 멤버로 삽입됩니다.
- vptr은 해당 객체의 클래스의 vtable을 가리키는 포인터입니다.
- 객체 생성시 vptr은 해당 객체의 클래스의 vtable을 가리키도록 초기화됩니다.

#### 가상 소멸자, virtual destructor
- Parent 클래스의 포인터를 통해 Child 클래스의 객체를 삭제할 때, Child 클래스의 소멸자가 호출되지 않으면 메모리 누수가 발생할 수 있습니다.
- 이를 방지하고자 virtual 키워드를 사용할 경우 반드시 소멸자에도 적용해주어야 합니다.
- 이 경우 Child 클래스의 소멸자가 먼저 호출된 후, Parent 클래스의 소멸자가 호출됩니다. 

### 동적 디스패치, dynamic dispatch
- 동적 디스패치는 런타임에 올바른 함수를 호출하는 것을 의미합니다.
#### 디스패치
- 호출할 함수를 결정하는 것을 의미합니다
### 정적 디스패치(static dispatch, early binding) 
- 클래스의 함수를 정의하면 컴파일러는 함수를 호출할 때마다 이를 실행합니다.
- 이는 컴파일 타임에 디스패치가 이루어지므로 비교적 속도가 빠릅니다.

### 순수 가상 함수(pure virtual function) 그리고 추상 클래스(abstract class)
- 반드시 재정의해야 하는 가상함수를 의미합니다.
```C++
virtual void function01() = 0;
```
- '= 0'을 사용하여 선언툅니다 
#### 추상 클래스 
- 순수가상함수를 포함하는 클래스를 의미합니다
- 직접 인스턴스화 할 수 없으며, 파생 클래스를 통해서만 인스턴스화할 수 있습니다.

# 설계 원칙
#### SRP, Single Responsibility Principle, 단일 책임 원칙
- SW 모듈은 변경의 이유는 하나, 단 하나여야만 한다.

#### OCP, Open-Closed Principle, 개방-폐쇄 원칙
- 기존 코드를 수정하기보다는 반드시 새로운 코드를 추가하는 방식으로 시스템의 행위를 변경할 수 있도록 설계해야만 SW 시스템을 쉽게 변경할 수 있다

#### LSP, Liskov Substitution Principle, 리스코프 치환 원칙
- 파생 클래스는 Basic 클래스를 대체할 수 있어야 한다.

#### ISP, Interface Segregation Principle, 인터페이스 분리 원칙
- SW 설계자는 사용하지 않은 것에 의존하지 않아야 한다 -> 사용하는 인터페이스만 구현하라.

#### DIP, Dependency Inversion Principle, 의존성 역전 원칙
- 고수준 정책을 구현하는 코드는 저수준 세부사항을 구현하는 코드에 의존해서는 안된다. -> 모듈간의 의존성을 인터페이스로 향하게 하라.

# 컴포넌트 응집도와 관련된 원칙
- 설계 원칙과 비슷한 부분이 많다.
#### REP, Reuse/Release Equivalence Principle, 재사용/릴리즈 등가 원칙
- 재사용과 릴리즈는 같은 단위여야 한다. -> 하나의 컴포넌트로 묶인 클래스와 모듈은 반드시 함께 릴리스할 수 있어야 한다
#### CCP: Common Closure Principle, 공통 폐쇄 원칙
- 같은 이유로 같은 시점에 변경되는 클래스는 같은 컴포넌트로 묶어야 한다. Inverse도 성립한다.
#### CRP: Common Reuse Principle, 공통 재사용 원칙
- 컴포넌트 간의 의존성은 속한 모든 클래스에 적용되기에, 결합이 약한 클래스들은 다른 컴포넌트로 분리해야 한다.

# 컴포넌트 결합과 관련된 원칙
## 의존성
- A->B, A가 동작하기 위해 B를 필요로 하는 관계
#### 타입 의존성, Type Dependency
- 참조 대상의 클래스 타입이나 메모리 레이아웃 구조에 직접 결합하는 의존성
#### 행위 의존성, Behavior Dependency
- 참조 대상의 메서드 이름, 매개변수, 반환 타입에 결합하는 의존성

### 정적/동적 타입에서의 의존성
#### 정적 타입 언어
- 컴파일 시점에 물리적 크기와 상속 관계를 모두 검증하기 때문에, 타입 의존성과 행위 의존성을 모두 강제당합니다
- 가상 함수를 통해 타입 의존성을 해제할 수 있습니다
#### 동적 타입 언어
- 컴파일 시점의 타입 검증이 없으므로 타입 의존성이 없으며, 런타임 행위 의존성만 강제당합니다.

## ADP,Acyclic Dependencies Principle, 의존성 비순환 원칙
- 컴포넌트 의존성 그래프에 순환이 있어서는 안된다 
-> 순환 의존성 컴포넌트 하나를 수정하면 그로 인한 다른 컴포넌트의 오작동 - 수정이 순환될 수 있다.
### 순환 의존성을 제거하는 방법
- 개발 환경을 릴리즈 가능한 컴포넌트 단위로 분리한다
- 해당 컴포넌트에 릴리즈 번호, 버전을 부여한다
- 다른 팀은 릴리즈된 버전을 사용한다
- 새로운 릴리즈마다 사용여부를 결정한다

#### 효과
- 어떤 팀도 다른 팀의 컴포넌트 개발 상황에 좌우되지 않는다
- 이 방법은 컴포넌트 사이의 의존성 구조를 계속해서 관리(순환 제거)해야 사용 가능하다.

### 순환을 제거하는 방법
#### DIP(의존성 역전 원칙) 적용
#### 공통으로 의존하는 새로운 컴포넌트 생성
- 새 컴포넌트를 만들고 순환이 형성된 두 컴포넌트가 의존하는 클래스들을 이동시킨다.

### 결론
- 순환을 제거하는 방법에서 보았듯, 컴포넌트는 시스템이 성장할 때 함께 진화한다.
- 컴포넌트 의존성 다이어그램은 빌드 가능성과 유지보수성을 보여주며, 기능과는 거리가 멀다.
- 따라서 컴포넌트는 하향식으로 설계될 수 없다.
#### 한줄 요약
- 컴포넌트 의존성 구조는 개발 과정에서 계속해서 다듬고 수정해야 한다.

## SDP, Stable Dependencies Principle, 안정된 의존성 원칙
- 안정된: 외부 요인에 의해 쉽게 변경되지 않는, 영향을 안받는
- 더 안정된 컴포넌트에 의존하라
- 안정성의 방향으로 의존하라
### 불안정성 지표
#### 용어
- Fan In: 안으로 들어오는 의존성, 나를 참조하는 외부 클래스의 개수
- Fan Out: 바깥으로 나가는 의존성, 내가 참조하는 외부 클래스의 개수
- I, Instability: Fo/(Fi + Fo)
#### 설명
- C++에서 각 소스 파일이 하나의 클래스로만 구성되어있을 경우, include를 세면 쉽게 I를 계산할 수 있다.
- SDP에 따르면 I 지표는 해당 컴포넌트에 의존하는 다른 컴포넌트의 I 지표보다 커야한다.
- DIP, 의존성 역전 원칙을 적용하면 I 지표값을 조정할 수 있다.
- 정적 타입 언어(컴파일 시점에 타입을 결정)에서 가상함수를 사용하여 DIP를 적용할 수 있다
- 동적 타입 언어는 타입 의존성이 애초에 없다

## SAP, Stable Abstraction Principle, 안정된 추상화 원칙
- 컴포넌트는 안정된 정도만큼만 추상화되어야 한다
- 안정적인 컴포넌트는 반드시 인터페이스와 추상 클래스로 구성되어 쉽게 확장 가능해야한다.
### 고수준 정책은 어디에 두어야 하는가
- 변경을 최소화 하고 싶은 SW는 안정된 컴포넌트에 두어야 한다
- 변경사항이 자주 발생하는 SW는 비교적 불안정한 컴포넌트에 두어야 한다.
### 추상화 정도, A
- A(0~1) = 컴포넌트의 추상 클래스와 인터페이스의 개수 / 컴포넌트의 클래스 개수
- 컴포넌트가 위치할 수 있는 가장 바람직한 지점은 (I,A)가 (1,0), (0,1) 두 지점이다.
- 종점에 위치할 수 없다면 두 지점을 잇는 선에 가깝게 위치할 때 이상적이다.
### 주계열과의 거리, D
- I와 A를 축으로하는 이차원 공간에서, (1,0), (0,1)을 잇는 선을 주계열이라고 하자.
- D = |A + I - 1|
- D는 0 ~ 1 사이의 값을 가지며 0일 경우 컴포넌트가 주계열 바로 위에 위치한다.
- 모든 컴포넌트의 D 지표의 분산을 통해 관리 한계(control limit)를 결정하기 위한 목적으로 사용할 수 있다.
- 모든 컴포넌트의 D 지표의 분산을 구하고, 아키텍쳐가 설정한 값(control limit)을 벗어난 컴포넌트를 검토하여 설계 문제를 발견할 수 있다.
